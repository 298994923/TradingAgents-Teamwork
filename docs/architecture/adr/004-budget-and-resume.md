# 004-budget-and-resume.md

**C main candidate v0.2 · Proposed, not adopted · 2026-11-23**

## Context and scope

The adoption target is `main@54bb43bdb14385d55366ae0f365b602ac4cd2273`. `C-keyed-checkpoint-graph-review-package.md` v0.1 was reviewed against `integration@a61b7b587169bcfb20300be1b95f721e1a496caa`; its results below are historical, not main acceptance. On main, runs with the same ticker, date, and compatibility signature share a thread. A caller needs to distinguish otherwise identical runs without invalidating existing checkpoints or changing what makes a run compatible.

Main has ADR-005 for the deterministic guard, but not ADR-003 for review/context or the budget/resume ADR and execution-budget contract referenced by `AGENTS.md`. This two-document candidate adds the missing ADR and contract; it does not authorize editing a protected file. The keyed lifecycle changes no budget behavior. The V2 research-budget addendum is separate and follows initial ADR adoption.

## Proposed decision

1. Add optional keyword-only `run_key: str = ""` to `TradingAgentsGraph.propagate()` and carry it per call through `checkpoint_scope()`, `begin_checkpoint()`, `_run_graph()`, and `clear_checkpoint_on_success()`. Use the same key with the existing C storage helpers for thread ID, saved-step lookup, and cleanup. Inject that exact thread ID into invocation config. If that thread has a resumable step, resume with `None` and execute only pending work; if there is no resumable step, use the existing programmatic fresh-run behavior for the requested thread, without falling back to a sibling or legacy thread.
2. Keep `_run_signature()` and its compatibility inputs unchanged. `run_key` selects a run within the same compatibility namespace; it does not relax compatibility or replace the signature. Omitted and empty keys preserve the exact legacy ID and behavior. Nonempty keys use the storage candidate's versioned, structured encoding of ticker, date, signature, and key, without changing the per-ticker SQLite location. Callers choose distinct keys for distinct runs and repeat the original key to resume.
3. Keep the disabled-checkpoint early return before SQLite access, with or without a key. On normal programmatic success, keep the existing cleanup order and use the same ticker, date, signature, and key to remove only that thread's rows in `checkpoints` and `writes`. Preserve sibling keyed and legacy rows. This is derived-key cleanup, not the separate locator-based exact-thread cleanup API or a new manifest-publication guarantee.
4. Do not alter the constructor or the legacy report path. Preserve `on_prompt` forwarding and B's actual Bull, Bear, and Research Manager receipts where that wiring exists. It exists on the reviewed integration baseline but not on the pinned main baseline; do not add it as part of keyed checkpoint work. The receipt control verifies digests of the prompts the model saw; it does not establish a pre-invocation prompt-compatibility fingerprint.

This adoption candidate has no production edits. For the separate graph implementation, only `src/tradingagents/graph/trading_graph.py` is proposed for production edits. Main's graph and storage helpers do not yet accept `run_key`. The C storage candidate at `e611e0daefa91257a1fd01d7410afc2f45160901` was exercised in a disposable integration checkout and remains a separate prerequisite on main. V1 selection, CLI, Evidence binding, locator recovery, manifest publication, budget admission and routing are out of scope.

## Existing decisions and approval boundary

`D-to-C-review-checkpoint-compat.md` distinguishes legacy automatic continuation from explicit adaptive recovery: an incompatible explicit recovery must make the mismatch visible, invoke zero nodes, and preserve the old checkpoint. `E-to-C-evidence-checkpoint-response (2).md` §8 and `C-evidence-checkpoint-recovery-plan.md` separately track locating the original run, Evidence verification, and preserving the checkpoint until successful terminal publication. This proposal neither implements nor changes those rules. ADR-005, `005-deterministic-guard.md`, still governs the guard and is not authorization for this graph edit.

`D-to-C-keyed-checkpoint-ruling.md` approves review package v0.1 and both pinned tests for the reviewed scope. Its authorization for `trading_graph.py` is conditional: ADR adoption after team visibility, the required review and verification records, and the guard lineage rule must all be satisfied for the actual delivery. A resumed run may publish a restored `guard_result` only from its own gates; `executable=true` must originate from that run's Portfolio Manager final-gate PASS. This main candidate does not record new approval, adopt the ADR, or authorize source edits.
